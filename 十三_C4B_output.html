我给作业求解器加了一个"自己检查自己"的功能

导读：做作业自动化，最容易想到的流程是：读题→解题→排版→交。

一个求解器最危险的不是解错题，而是解错了还排版得很漂亮。
这篇讲我怎么把"验证"从人工复核挪进流水线，以及自校验怎么抓出我自己写的 bug。

从一个真实的痛点说起

做作业自动化，最容易想到的流程是：读题 → 解题 → 排版 → 交。

但我在给 C4C（作业自动求解与排版）写求解器的时候，意识到一个问题：

我的程序解出来的答案，谁来确认它是对的？

如果靠人工复核，那这个工具的价值就打了对折——你还是要一道一道看。
如果靠"程序自己说对"，那它解错了也会很自信地告诉你对了。

更麻烦的是排版。一份排版精良的 PDF 会让人默认它是对的。
把错误的答案排得整整齐齐，比把错误的答案乱糟糟地摆着，危险得多。

所以我把"验证"做成了流程里的强制步骤

我的做法是：每解一题，立刻用另一条独立路径复算一次。

关键词是"另一条"。如果校验只是把同一个式子再跑一遍，那同一个 bug 会跑出同样的结果——那不叫校验，叫重复劳动。

题型 求解用 校验用
二次方程 求根公式 把根代回原方程，看是否归零
线性方程组 高斯消元 把解代回每一个方程
行列式 余子式展开 消元取主元之积（两种算法）
矩阵的秩 行最简形 rank(A) 与 rank(Aᵀ) 互验

最后两行是我后来加线性代数时补的。可以看到规律：求解和校验必须是两种不同的算法。

自校验真的抓到过我自己的 bug

这里有个真实案例。我给特征值求解写完代码，跑了一道很简单的题：

A = [[1, 1],
[1, 0]] # 斐波那契矩阵

⟨ python ⟩

这个矩阵的特征值是黄金比例：(1±√5)/2，也就是约 1.618 和 -0.618。

程序输出了：

λ ∈ {0.618034, -1.61803}

⟨ text ⟩

数值看起来非常合理，排版出来也很漂亮。如果你只是扫一眼，很可能就信了。

但它符号全反了。原因是我在处理剩余二次因子的时候，把系数 [a, b, c] 当成了 [b, c] 来用。

抓出这个 bug 的不是我的眼睛，而是这条不变量：

特征值之和必须等于矩阵的迹（trace）
Σλ = -1 但 tr(A) = 1 → 校验失败

⟨ text ⟩

程序自己发现不对，在 PDF 里用红框标出"这道题的结果不应采信"。

有一个 bug 是自校验抓不到的

另一个 bug 更隐蔽。特征多项式渲染的时候，我把符号逻辑写错了，输出变成了这样：

λ²7λ10 = 0

⟨ text ⟩

正确的应该是 λ² − 7λ + 10 = 0。负号整个丢了。

这个 bug 自校验抓不到——因为它验证的是"数学上对不对"，而负号丢在"写出来对不对"这一层。它是人工看 PDF 截图发现的。

这给了我一个很重要的提醒：

机器能验的部分要交给机器；机器验不了的部分，要诚实标出来，而不是假装全覆盖。

我总结的三条原则

  1. 校验必须走另一条算法。 同一个 bug 跑两遍还是同一个 bug。
  2. 校验不过的答案必须显眼地标出来。 排版精良的错误答案，比乱糟糟的错误答案危险得多。
  3. 机器验不了的要明说。 我的求解器会如实地告诉使用者"这一题没有自动校验"，而不是让它安静地混在正确答案里。

这套东西最后长什么样

输入一份结构化的题目文件，输出一份排版好的 PDF。每道题带求解过程、答案框、以及自校验结果。

它现在支持四类题型：一元二次方程、线性方程组、描述统计、线性代数（行列式、行最简形、特征值）。全程只用 Python 标准库，没有引入任何第三方依赖。

如果你也想做一个"能自己检查自己"的工具，我的建议是从第二条原则开始：先想清楚什么东西是你验证不了的——那往往比"我能做什么"更值得先写下来。
